# Domain Model

## Models

Models live in modules: `Ledger` (Account, Category, Transaction), `Planning` (Bucket, Allocation, Project, WishlistItem, Scenario, PlannedEvent, PlannedEventSeries, SavingsGoal, SavingsGoalContribution), `Identity` (User). See `architecture.md` for the boundary rules.

| Model | Notes |
|---|---|
| `User` | `currency_default`, `locale`, `timezone` drive formatting app-wide (see `preferences`). **"Today" is always the user's date**: `$user->today()` (or `User::todayFor($userId)` when only an id is at hand; no query for the signed-in user) returns a `CarbonImmutable` at midnight of the user's calendar date in their `timezone` (default `America/Bogota`, falling back to `config('app.timezone')` when empty or unknown), expressed in the app timezone so it compares directly with `date` columns. Never use `today()`/`now()` for a user's date: defaults for realize/purchase dates, overdue detection, projections, planner start, series horizon, cycle closing, auto-posting due-checks and "current month" on dashboards and reports all go through it. |
| `Account` | Bank/wallet/cash/credit-card/savings. `initial_balance` + the transaction ledger derive the live balance — balance is never a stored column (see `BalanceCalculator`). Optional `yield_rate` (percent per year) + `yield_compounding` (daily/monthly/yearly) model interest on real money only; the cash-flow projection simulates it with the pure `Planning/Support/YieldSimulator` (never stored, never a transaction). `on_budget` (default true) decides whether its balance counts toward *ready to assign* (an off-budget account is, for example, a long-term deposit). An account is **in the budget** while it is on budget and active (not archived); the same rule applies everywhere: `budgetBalances`, `LedgerQuery::isOnBudget` and the category spending of `expenseTotal(onBudgetOnly)`. When it enters or leaves the budget (toggle or archive), a model hook in `LedgerServiceProvider` fires `AccountBudgetChanged` (user id, account id, in budget) and Planning's `SyncAccountBudget` removes (or re-applies) the `spend` rows of its expenses paid from a bucket and of its wish-list purchases, so an account outside the budget touches no envelope. Income allocations it made stay in their buckets. Soft-deletes; deleting an account with transactions (trashed ones included, so they can always be restored) or used by an active repeating plan archives it (`is_active = false`) instead. An archived account takes no new transactions, transfers, auto-posting plans, realized plans or purchases; a transaction already on it can still be edited. `Transaction::account()`/`category()` include trashed rows, so a list never meets a null account. |
| `Category` | Income or expense. `user_id` nullable — `null` means a system category (seeded, shared by every user). Uses a **custom** `visibleToUser` global scope (owner OR `user_id IS NULL`), not `BelongsToUser` — see below. Soft-deletes; system categories and categories with transactions can't be deleted/edited (`Category::isEditable()`). A category still referenced by a bucket, an open planned event or a planned series (`Category::isUsedByPlans()`) can't be deleted or purged either, so those never meet a missing category; notifications still fall back gracefully (bucket name) for legacy rows. |
| `BucketCycle` | One cycle of a bucket. The open one only carries a per-cycle `cap_override`; a closed one is an immutable snapshot (`opening`, `filled`, `moved_in`, `moved_out`, `spent`, `released`, `closing`, `cap`) written by `BucketCycleService`. |
| `Bucket` | A virtual earmark of money (`spending` or `savings`), replacing `Budget`. Spending buckets track a `category` against a per-`cycle` `cap_amount` (monthly/yearly) exactly like budgets did; savings buckets hold funded money with an optional target. Optional `fill_rule` (fixed/percent/of_remaining/fill_to_target; `fixed` is per cycle when the bucket has a cycle, counting income already received in it via `BucketLedger::receivedInCycle`; `of_remaining` is a share of the still-unclaimed income) + `fill_value` claim income in `priority` order (a `fixed` value, and its step-up value, is money with at most 2 decimals; a percentage may have 4); `carry_over` (carry/release/overflow) decides what happens to the leftover when a cycle ends; `cycle_goal` (savings only: what it aims to receive each cycle), `cycle` (daily/weekly/monthly/yearly) + `cycle_every` + optional `cycle_anchor` define the repeating window (pure `Support/CyclePeriod`; month-end days clamp); `step_up_value` + `step_up_after_bucket_id` (a fill value that applies from the cycle after another bucket reaches its target or is completed; `BucketLedger::fillValueFor` compares the trigger's balance at the end of the previous cycle each time, so a trigger that later drops below its target switches back; the forecast engine treats the trigger as reached once its envelope holds its target and keeps it that way), `completed_on` + `completes_on_purchase` (a completed bucket takes no income; `BucketLedger::complete/reopen` move what is left to the overflow bucket or back to ready to assign, and buying its wish-list item completes it, also in the forecast engine); `allowed_account_ids` restricts which accounts' income can fill it. There is no catch-all bucket: income no rule claims stays *ready to assign* (the default bucket was retired by the `retire_default_buckets` migration, which deleted each one and pointed overflows, step-ups, wish-list items and plan splits that used it at ready to assign). Unique per user/category/currency/cycle. |
| `Allocation` | One signed line of the virtual money ledger (`income`, `planned`, `transfer`, `carry`, `spend`, `adjustment`, `opening`, `ready`). A `ready` row has no counterpart bucket: it is money exchanged with ready to assign (a release, an assignment, or the cover of an income removed after its money was used, then tied to that income). A bucket's funded balance is the sum of its allocations; for a category-linked spending bucket, *available* (its **envelope**) additionally subtracts the category's real spending in on-budget accounts since the bucket was funded (`BucketLedger::fundedSince`: the later of `tracking_started_on` and the stored `buckets.funded_since`). `funded_since` is set by an `Allocation` model hook when the first row is saved and moves earlier for a backdated row, never later: removing or redating the earliest allocation keeps the spending recorded since then in the envelope. `BucketLedger::forgetFundingIfUnused` clears it only when the bucket has no allocations left and its category had no spending since (nothing happened to that envelope, so it is a limit again); with spending since, it stays and the empty envelope shows as overspent (that spending was budgeted from it). A new opening balance is dated the user's today (not `tracking_started_on`), and `BucketLedger::assignEffect` gives the real change to ready to assign of putting money in (less the category spending a first or earlier funding brings into the envelope), which the over-assign guard uses. Without a date every recorded row counts, future-dated ones included, the same cut-off as account balances. |
| `SavingsGoal` | Target amount + optional target date. `status`: active/completed/archived. Soft-deletes. Has many `SavingsGoalContribution`; recording a contribution that reaches the target auto-flips status to completed. |
| `SavingsGoalContribution` | Belongs to a `SavingsGoal`; optionally linked to the `Transaction` it came from (`linked_transaction_id`, nullable). |
| `Project` / `WishlistItem` | A `Project` (project/hobby/category/other) groups wish-list items. It has one `currency` (its items must use it), an optional `budget_amount` and `target_date`, and an optional savings `bucket_id` (unique: one bucket serves one project; `ProjectManager` can make a new one, targeting the budget or what the wanted items cost). `WishlistItem::fundingBucket` is the item's own bucket or else its project's; purchases, the planner and the reports use it. A `WishlistItem` has a price, `importance` 1-5, optional `desired_by`, `bucket_id` (a savings bucket of the same currency), `allowed_account_ids`, and a `status` (wanted/purchased/dropped). Purchasing records a real expense through `RecordsTransactions::record` (with `bucket_id` = the item's bucket when the account is on budget, so it never also counts in a category envelope; `ExpenseSpending::withoutSpending` keeps the full-amount spend row out) plus a negative `spend` `Allocation` (capped to the bucket's available funds; the rest comes out of ready to assign) and stores both ids so the purchase can be undone together (`WishlistService`). When buying completes the bucket (`completes_on_purchase`), the allocations `BucketLedger::complete` created are kept in `completion_allocation_ids`; undoing reopens the bucket and takes that leftover back (all of a release to ready to assign; from the overflow bucket only what it still holds). Undoing removes the expense for good (`RecordsTransactions::forget`, no Trash). Deleting the expense from the ledger reverses the purchase (item `wanted`, spend removed, `purchased_transaction_id` kept); restoring it re-applies the purchase if the item is still wanted; purging it clears the id. |
| `Scenario` | A saved purchase order for the planner: a name, currency, `forecast_view` (conservative/expected/optimistic), `horizon_months` (12/24/36) and ordered `ScenarioLine`s (`wishlist_item_id`, `position`, optional `not_before`). Results are never stored; they are recomputed on demand. |
| `PlannedEvent` | A projected income, expense or transfer (`transfer_out` from `account_id` to `counter_account_id`, same currency, no category; realized through `RecordsTransactions::recordTransfer`, the outgoing leg's id is the link, so deleting or restoring either leg reopens or closes the plan; net zero per currency in projections, but it moves the yield simulation's balances) on a future date (`planned`/`realized`/`skipped`) with a `certainty` (confirmed/expected/speculative). **Never touches balances.** Realizing one records a real `Transaction` through `Ledger\Contracts\RecordsTransactions` and stores its id in `realized_transaction_id`; whatever the confirm leaves out comes from the plan (account, category, amount, description) and the date defaults to the planned date, or today for a plan dated later (a realized date is never after today). Deleting that transaction reopens the plan (`planned`, id kept); restoring it from the Trash closes the plan again unless it was realized by another transaction meanwhile; purging it clears the id and turns `auto_post` off on a plan left open, so it waits in needs review instead of recording itself again. `reopen` is only for skipped plans. Optionally part of a `PlannedEventSeries` (a repeating rule whose dates come from the pure `Planning/Support/Recurrence`; it materializes occurrences from the owner's today up to 12 months ahead; extended daily by `planning:extend-series`). `materialized_until` is the last date the rule created an occurrence for; top-ups and the virtual occurrences of `PlannedOccurrences` continue after it (not after the latest stored occurrence), so moving one occurrence to another date neither brings its old date back nor skips the dates in between. Pausing, an earlier end and a rebuilt rhythm move it back. Each occurrence stores `series_date`, the date its rule gave it (set when it is created, kept when that occurrence alone is moved; null for a plan that does not repeat), which is the date it stands for in a rebuild and in `excluded_dates` when it is deleted. A series whose start date is in the past keeps that date as its rhythm anchor, but its past occurrences are never created, so it does not flood the current month with overdue plans. A series keeps `notes`, an income's bucket split (`allocation_overrides`) and `auto_post` (record it automatically on its date) and copies them to every occurrence it creates; each occurrence keeps its own `auto_post` (so a one-off plan can auto-post too) and `post_error`. Auto-posting needs an active account and a category (`PlannedRules`). An inactive (`is_active = false`, paused) series creates no occurrences. A series is edited as a whole from the owner's today on (`PlannedEventService::updateSeries`, `PATCH planning/series/{id}`): plain fields change its open occurrences dated today or later; a new frequency or next date sets `starts_on` to that date and rebuilds those occurrences from today (keeping overdue, realized and skipped ones, and only past `excluded_dates`; each realized or skipped occurrence dated today or later, or standing for a date from today on, uses up the new rule's date closest to its `series_date`, only within half of the shorter of the old and new periods (weekly 3 days, biweekly 7, monthly 15, yearly 182; `RecurringFrequency::halfPeriodDays`), the later one on a tie, and never the next date the user just typed unless its `series_date` is exactly that day (pure `Recurrence::claimed`); the dates used up are added to `excluded_dates`, so nothing is planned twice and no other date is lost. The candidates ignore `excluded_dates`, so rebuilding again (a second pause and resume) changes nothing); an earlier `ends_on` (also the one deleting an occurrence "and all future ones" sets) removes later open occurrences and adds the `series_date` of each realized or skipped one kept after it to `excluded_dates`, so removing the end later never plans those dates again; turning auto-post off clears it on every open occurrence. Pausing deletes the open occurrences from today on and stops overdue ones from auto-posting; resuming creates them again from today (never in the past; realized or skipped occurrences from today on use up their dates the same way); deleting a series removes its open occurrences and keeps realized and skipped ones as history (`series_id` becomes null). Deleting one occurrence hard-deletes the row and remembers its `series_date` (its rule date, also when it was moved) in the series' `excluded_dates`, so extending never recreates it; a `skipped` event is a visible user action that can be reopened. Replaces the old `BudgetForecast`. |
| `Transaction` | `type`: income / expense / transfer_out / transfer_in. A transaction dated after the user's today is accepted from the form only when resent with `confirm_future` (`GuardsFutureDates`, error `transactions.future_date_confirm` on `date`; an edit is asked only when it changes the date; CSV imports, bulk edits and system postings are not asked, and a realized plan is never dated after today). `is_recurring_generated` marks one the app recorded by itself (auto-posted); the monthly report counts it, and any expense confirmed from a repeating plan, as a fixed expense. A transfer is always **two rows** sharing a `transfer_group_id` (see `TransactionService::createTransfer`) — never a single row with a "to account" column. `category_id` is null only for transfer rows. Optional `bucket_id` (expenses only, `nullOnDelete`): the bucket that paid for it, a bucket without a category, not completed, in the account's currency (`Shared/Validation/PlanningRules::spendableBucket`; an edit may keep the bucket the expense already has even if it was completed or gained a category since; such an expense keeps its `spend` row and, having a `bucket_id`, stays out of the category's envelope spending, so it is counted once), never on an off-budget account. Planning's `ExpenseSpending` keeps one `spend` allocation of the full amount (it may overspend) tied to the transaction, redone on `ExpenseRecorded`/`ExpenseRemoved`; a linked expense no longer counts in its category's envelope. Soft-deletes. |

**Currencies never mix** (there is no exchange rate): a transfer's two accounts must share a currency; a transaction can't move to an account in another currency (`TransactionService::reassign` skips it in bulk); an account's currency is locked once it has transactions (trashed ones included) or a planned event, planned series or a bucket's or wish-list item's `allowed_account_ids` uses it (`Account::isCurrencyLocked()`), and a bucket's once it has allocations; a bucket's or wish-list item's `allowed_account_ids` must be in its currency; a plan is realized into, or linked to a transaction of, an account in the plan's currency.

Cross-module events from `Ledger`: `TransactionsMutated`, `IncomeRecorded`, `IncomeRemoved`, `ExpenseRecorded`, `ExpenseRemoved` (create/restore/delete, and an edit of account, amount, date or bucket; they carry the bucket id), and per transaction leg `TransactionDeleted` (soft delete), `TransactionRestored` (back from the Trash) and `TransactionPurged` (just before a force delete), plus `AccountBudgetChanged` (an account entered or left the budget; ids and a flag only). They carry ids and primitives (user, transaction id, type, account id, amount, date), never a Ledger model; Planning's listeners use them to keep realized plans and wish-list purchases in step with their transactions.

All models except `Category` (and the join-only `SavingsGoalContribution`) use the `App\Modules\Shared\Concerns\BelongsToUser` trait.

## `BelongsToUser`

```php
trait BelongsToUser
{
    protected static function bootBelongsToUser(): void
    {
        static::addGlobalScope('user', fn (Builder $builder) =>
            Auth::check() && $builder->where($builder->getModel()->getTable().'.user_id', Auth::id()));

        static::creating(fn ($model) => $model->user_id ??= Auth::id());
    }
}
```

Every query against a `BelongsToUser` model is transparently scoped to the authenticated user — including **implicit route-model binding**. This has a consequence that shows up throughout the controllers and their tests: **an authenticated user requesting another user's resource by ID gets a 404, not a 403** — the row is invisible to the query before a Policy ever runs, not merely forbidden. Only `Category`'s custom scope (owner OR system) and cases where a Form Request's `exists:` rule bypasses Eloquent scopes entirely (see below) deviate from this.

Use `Model::forUser($user)` (also from the trait) to query outside a request context (jobs, console commands) where `Auth::check()` is false.

Because the scope silently turns off without an authenticated user, any code reachable from a queued job, console command or a listener they trigger must scope explicitly. `Ledger\Contracts\LedgerQuery` therefore takes the user id on every method (`expenseTotal($userId, ...)`, `accountCurrency($userId, ...)`, ...), and Planning services pass `$bucket->user_id` / the event's user rather than relying on `Auth`. `Category::visibleTo($userId)` is the explicit form of the category scope (own + system). `BackgroundTenancyTest` runs the cycle-close command and the auto-post job with two users sharing a system category.

## Validation must re-scope `exists:` rules

`exists:accounts,id` / `exists:categories,id` in a Form Request checks **only that a row exists**, not that it belongs to the current user — Laravel's `exists` rule runs a raw query, bypassing the `BelongsToUser` global scope entirely. Every Form Request that accepts an `account_id` or `category_id` foreign key scopes it explicitly:

```php
'account_id' => ['required', 'integer', Rule::exists('accounts', 'id')->where('user_id', $this->user()->id)],
'category_id' => ['required', 'integer', Rule::exists('categories', 'id')
    ->where(fn ($query) => $query->where('user_id', $this->user()->id)->orWhereNull('user_id'))],
```

(Categories additionally allow `user_id IS NULL` — system categories are valid for everyone.) Both rules must also exclude soft-deleted rows (`whereNull('deleted_at')`), or a trashed account or category passes validation. Ledger requests that take a bucket use `App\Modules\Shared\Validation\PlanningRules::spendableBucket($userId, $currency)` the same way. Use `App\Modules\Shared\Validation\LedgerRules::account($userId, activeOnly: ..., keepId: ...)` and `LedgerRules::category($userId, $type, keepId: ...)` (`keepId` lets an edit keep the category the record already has, even if it was deleted since), which do all of this (passing the transaction's or plan's type makes the category match it: an income never lands in an expense category; spending buckets and purchases take expense categories only); `activeOnly` also rejects archived accounts for anything that creates new money movements. If you add a new Form Request with a foreign key onto a `BelongsToUser` model, scope it the same way — a bare `exists:table,id` is a cross-tenant data leak, not just a style nit. This exact gap existed in the original Livewire app and was only caught while writing Phase 8's feature tests (see `testing-conventions.md`).

## Key services (inside their modules)

- **`TransactionService`** (Ledger) — the only code path allowed to write a `Transaction`. Owns transfer double-entry (`createTransfer`/`updateTransfer`/`delete` all keep both legs of a transfer in sync or delete them together) and dispatches `TransactionsMutated` so caches invalidate.
- **`BalanceCalculator`** (Ledger) — derives account balances and net worth from `initial_balance` + the ledger. Only per-account balances are cached (Redis, 1h TTL); net worth is summed from them on every call, so archiving or deleting an account drops out at once. `forgetAccount()` clears the key immediately and again after the open DB transaction commits or rolls back (so a balance a listener read inside a failed transaction never stays cached). It runs on every `TransactionsMutated` and, through model hooks registered in `LedgerServiceProvider`, whenever an `Account` is saved, deleted or restored (initial balance, currency, archive). Don't fire `TransactionsMutated` for account edits: it also triggers notification listeners.
- **`PlannedEventService`** (Planning) — creates events/series, edits and deletes with `this`/`future` scope, realizes, skips and links plans, and suggests matching real transactions (a similar transaction from 5 days before to 5 days after the plan's date, or up to today for an overdue plan but never more than 10 days after its date). `CashFlowProjector` (Planning) projects balances per month and currency for a `ForecastView` (conservative = confirmed income only, expected = + expected, optimistic = all; expenses always count). `ForecastView::default()` (Expected) is the view every page and service uses when none is chosen; `ForecastView::fromRequest()` reads `?view=` with that fallback.
- **`PlannedOccurrences`** (Planning) — the single source of open planned money for every projection (`CashFlowProjector`, `ForecastInputBuilder`, planned expense totals): `open(user, until, ?currency, ?type)` returns the open stored plans up to a date plus the occurrences active series will create after `materialized_until` (the last date each one created, not its latest stored occurrence) (series are stored 12 months ahead; the planner can look 36), as pure `Support/ProjectedItem`s. `ProjectedItem::effectiveDate(today)` is the one place where an overdue open plan counts as happening today.
- **`ForecastInputBuilder`** (Planning) — the one place that turns real money and plans into forecast input for one currency (`build(user, currency, view, until)` → `ForecastInputs`, memoized per request): start cash = the active on-budget accounts (`Balances::budgetBalances`), every bucket as a pure `EngineBucket` (envelope from `BucketLedger::availableMany`, `isFunded` = `funded_since` set, the effective funded-since day, cap overrides of the current and later cycles), and the open planned money as `EngineFlow`s on their effective dates: incomes the view trusts that land in the budget (on-budget account or none; off-budget ones are only counted in `ForecastCoverage`), expenses that leave it, and planned transfers that cross its edge (`boundary`, signed). Projected interest is never part of it. `CashTimeline` (pure) gives end-of-day cash from those flows and the lowest it gets from a day on. `CashFlowForecast::budgetMonthly` projects the same on-budget cash month by month, written separately from the builder (only `PlannedOccurrences` and the on-budget accounts are shared) so the two can check each other.
- **`SeriesPoster`** (Planning) — records auto-posting plans (`planned_events.auto_post`) as real transactions once their date is the owner's today or earlier (hourly unique `PostDuePlannedEvents` job, every missed date in one run, each on its own date; and `postDueForUser` right after a plan with auto-post is saved). It goes through `PlannedEventService::realize(event, [], autoPosted: true)`, which locks and re-reads the plan and returns null when it is no longer open, so a run never records a plan twice, also against a confirm from the web. A plan whose account is archived or deleted or whose category is deleted gets `post_error` (`account_inactive`, `category_missing`; any other exception is reported and gives `failed`), a logged warning and, only when the reason changes, a `Planning\Events\PlannedPostingFailed` (once per series: an occurrence whose sibling already carries the same `post_error` raises none); it is retried on the next run and the error is cleared once it posts, or when the plan (or its series, for the occurrences the edit changes) is edited. A plan reopened because its transaction went to the Trash (still holding `realized_transaction_id`) is never auto-posted again; it waits in needs review, and restoring the transaction closes it. Auto-posted transactions have `is_recurring_generated = true` (the column keeps its old name and now means "auto-posted"). Repeating plans replaced recurring transactions: the `migrate_recurring_transactions_to_series` migration turned every template into a confirmed auto-posting series starting on its next due date (re-anchored only where the old "no overflow" chaining bent the rhythm: a month-end template drifted to the 28th goes back to its day, a 29 February goes back to the leap day; the first occurrence stays in the next due date's month. Known ambiguity: a next due date the user moved by hand to the 28th-30th of a template whose day is later looks the same as drift and is re-anchored to that day), with open occurrences from its next due date (so a template that was behind is caught up by the poster, with no cap on the missed dates); a template the old generator could not post (account archived or deleted, category deleted) became a paused series without occurrences, and dropped `recurring_transactions` and `transactions.recurring_transaction_id` (irreversible; drain the queue before deploying). `planning/recurring` redirects (301) to the repeating plans on the cash-flow page.
- **`PlannerService`** (Planning) — builds engine input with `ForecastInputBuilder` (on-budget cash, bucket envelopes, planned flows for the `ForecastView`), adds wish-list items as lines (`blocked` = item and bucket accounts do not overlap) and presents results. The maths lives in pure classes under `Planning/Support/Forecast`. `ForecastEngine` simulates free money (ready to assign = cash − funded envelopes, never stored): planned incomes go through `IncomeStep` (the same split the real `IncomeAllocator` makes; a never-funded bucket starts its envelope from zero on its first allocation), planned category expenses shrink every funded spending bucket tracking the category, boundary transfers move cash only, cycles close with their carry-over, and scenario lines are bought strictly in order at the earliest day their bucket (first) plus free money pay for them *and* the cash guard holds: the price fits in the lowest end-of-day cash from that day on (`CashTimeline::suffixMin`) minus what earlier purchases spent. Same-day order: flows, cycle closes, purchases. A later dip of free money below zero is reported (`freeDipsOn`), not blocked. `run(..., parkUnaffordable: true)` (user-built orders only, `PlannerService::simulate`) moves the first item that is never bought to the end, marked `parked`, and runs again, until only parked items follow; suggestions are never parked. The engine reuses work between runs over one input (`EngineMemo`): the purchase-free days are simulated once, and the state right after each purchase is kept by the lines bought so far, so the suggester's orderings that share a beginning resume from it instead of simulating it again. `ScenarioSuggester` scores orderings (importance-weighted waiting days, a penalty for items not bought within the horizon and for lateness) and tries every permutation up to 6 items, then local search.
- **`PlanningReportService`** (Reporting) — the only place where recorded history (`ReportService`) and projections (Planning contracts) meet; keeps them under separate keys so a page never mixes real and projected numbers.
- **`BucketService`** (Planning) — limit tracking for spending buckets (`progress()`: spent/remaining/percentage/status on_track/near_limit/exceeded for the current cycle). `BucketLedger` is the allocation ledger (balance, available/envelope, credit, move, releaseToReady); `BucketManager` saves/deletes buckets keeping the invariants; `IncomeAllocator` splits each income with the pure `IncomeStep` (the same step the forecast uses, built on `Waterfall`) when a Ledger `IncomeRecorded` event fires (only if some bucket has a rule; planned incomes may carry explicit per-bucket overrides, which are reused whenever the income that realizes or is linked to the plan is allocated again). `TransactionService::updateSimple` releases and re-allocates an income only when a money field (amount, account, date, type) is dirty, and does it in one DB transaction. Unclaimed income stays ready to assign, and income in an off-budget account is never allocated. `IncomeAllocator::release` never pushes a bucket below zero: when part of the income was already moved, spent or carried away, the bucket is topped back to zero by a `ready` allocation tied to the income (`source_id` = transaction id, description `buckets.release_shortfall`), so the shortfall shows as a lower (possibly negative) ready to assign. Allocating the income again (an edit, a restore, a linked plan) first takes that cover back, computes the split as before, and covers again only what is still missing, so a date-only edit or delete + restore ends exactly where it started. Covers written before the default bucket was retired were moves from that bucket; `retire_default_buckets` turned them into plain `adjustment` rows (description `buckets.release_shortfall`) without the income's id, which was never stored, so allocating that income again cannot take them back: they stay as manual entries the user can remove in the bucket's activity. A plan's explicit split only applies while the plan is `realized`, and only to buckets the income's account may fill and that are not completed; skipping or editing a plan whose transaction is in the Trash forgets that transaction. A negative manual adjustment is checked against `available()`, like a move; money put into a bucket from ready to assign (a starting amount, a positive adjustment, a move from ready to assign, a reset of an overspent envelope, removing a money-out entry: `BucketLedger::removalEffect`) goes through `AssignGuard::wouldOverAssign`, which makes the request answer with an `over_assign` error until it is resent with `confirm_over_assign` (a soft warning, never a hard limit); `BucketCycleService` (hourly `planning:close-bucket-cycles`, each bucket judged by its owner's today, so a cycle closes after it ends in the user's timezone) closes every finished cycle in order (catching up on missed ones), writes the `BucketCycle` snapshot and applies carry-over (release = a `ready` row back to ready to assign; purchases paid from the bucket count as spent); `BucketProjection` runs the forecast engine (no purchases) to the end of every bucket's current window (its cycle, or the calendar month) and reports the *provisional* fill from open planned income (never stored), what it holds at the end, the expected release or overflow and what other buckets pass to it (`project`), and what funded envelopes are projected to hold on given days (`earmarksAt`); `Bucket::effectiveCap()` honours a limit set for one cycle.
- **`ReportService`** (Reporting) — the aggregation layer behind the dashboard and the three report pages (monthly/annual/custom): period totals, expense-by-category, expense-by-account, net-worth evolution, etc. Every aggregate is a `Collection` **keyed by currency** — amounts in different currencies are never summed together.
- **`InsightService`** (Reporting) — turns `ReportService`'s numbers into short, translated sentences ("You spent 12% more than last month"). Every phrase is a parametrized `__()` call over real aggregates, never freeform text.
- **`TransactionImportService`** (Ledger) — parses/validates/imports a CSV of income/expense rows. Dates are parsed strictly (`checkdate`, no roll-over); amounts accept either separator, resolving a lone `d,ddd`/`d.ddd` with the user's `UserFormat::decimalSeparator()`, and reject exponents, more than two decimals and values beyond `decimal(15,2)`. The confirm endpoint validates row shape and the 1000-row limit again. Never writes a `Transaction` directly; hands validated rows to `TransactionService` so import-created transactions go through the exact same path as manually-created ones.

## Planned money

One form (`MoneyMovementForm`) records money that **already happened** (a `Transaction`) or is **planned** (a
`PlannedEvent`, optionally one occurrence of a `PlannedEventSeries`). A plan never touches a balance; it ends in one of:

- **confirmed** (`realize`): a real transaction is recorded from it, by the user (one click when it has an account and
  a category) or by `SeriesPoster` when `auto_post` is set and its date is the owner's today;
- **matched** (`link`): tied to a transaction the user already recorded;
- **skipped**: it will not happen (can be reopened);
- deleted.

A plan whose date has passed while still open, or that could not auto-post (`post_error`), is in the **needs review**
inbox (`UpcomingPlans::needsReview`, shown on the cash flow page, the dashboard and as the sidebar badge) and counts as
happening today in every projection (`ProjectedItem::effectiveDate`). Every projection reads open plans through
`PlannedOccurrences`, which adds the not-yet-stored dates of active series, so any horizon sees the same money. A series
is a rule: edited from today on, paused or resumed, never back-posting; stored history (realized and skipped
occurrences) is never rewritten. The transactions list shows the next 30 days and the overdue plans above it, labelled
as projected; real and projected totals are never mixed.

## Money map (ready to assign)

Envelope budgeting, per currency, **computed and never stored**:

- *in accounts* = Σ balances of active, on-budget, non-deleted accounts (`Balances::budgetBalances`; every recorded transaction counts, future-dated ones included);
- *in buckets* = Σ envelopes of **funded** buckets (`funded_since` set; a limit-only spending bucket is a limit, not earmarked money). An envelope is Σ allocations, minus, for a spending bucket with a category, that category's spending in accounts in the budget (on budget, not archived) since `fundedSince`, not counting expenses paid from a bucket (`BucketLedger::envelope`);
- *ready to assign* = in accounts − in buckets. Signed and never clamped, so in accounts = in buckets + ready to assign always holds; a negative value is shown as over-assigned.

The pure `Planning/Support/MoneyMap` does the sums; `Planning\Contracts\MoneyMap` (`MoneyMapService`) feeds it and is shared to every page as the deferred `moneyMap` prop, so it takes a constant number of queries however many accounts and buckets there are: `budgetBalances` reads every cached balance at once and computes the missing ones in one grouped query, and `BucketLedger::availableMany` gets every envelope from one grouped allocation sum plus one `LedgerQuery::budgetSpending` query (one conditional sum per category window); `ReadyToAssignTest` pins the count. Money reaches ready to assign implicitly (income no bucket claims, deleting a bucket, a transfer from an off-budget account) or through a `ready` allocation (cycle release, completion, income shortfall cover); money leaves it through allocations into buckets, which `AssignGuard` warns about when they would over-assign. `MoneyMapInvariantTest` checks, after every kind of money mutation, the three figures worked out by hand for that step and an independent recount from the raw tables; `EnvelopeFundingTest` and `EnvelopeSpendingTest` pin single envelopes the same way (expected values are always hand-computed, never recomputed with the formula under test).

## Money

`App\Modules\Shared\Support\Money` is an immutable, bcmath-backed value object — amounts are never manipulated as PHP floats. `Money::of()` rounds input with more than two decimals half away from zero (and writes floats out in full, so no `1.0E-5` reaches bcmath); `multiply`/`divide` truncate, so split parts never add up to more than the whole. Every money field a user types is validated with `App\Modules\Shared\Validation\MoneyRules` (`positive()`, `nonNegative()`, `signed()`): `decimal:0,2` rejects exponents and sub-cent input, and the bounds keep it inside `decimal(15,2)`. `App\Modules\Shared\Casts\AsMoney` is the Eloquent cast used on every money column (`amount`, `initial_balance`, `target_amount`, ...): reading the attribute returns a `Money`, writing accepts a `Money`, numeric string, or float. **Controllers must call `->toFloat()` (or `->toDecimalString()`) before putting a `Money` into an Inertia prop or JSON response** — Inertia doesn't know how to serialize it.
